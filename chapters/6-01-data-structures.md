# 6-01 数据结构：软件怎么"记"

> 第五部分带我们看数学如何照亮物理、化学、经济、生活。这一部分，我们走进一台机器内部，看「程序」到底由什么构成。先立一句总纲，它会是本部分的骨架：**计算机 = 硬件 + 软件；软件 = 数据结构 + 算法。** 数据结构管「怎么放」，算法管「怎么算」——本章先解决「放」的问题。你会看到，程序员口中那些神秘的名词（数组、链表、哈希表），拆开全是同一个朴素的念头：**把数据摆对地方，后面就省事。**

---

## 1.1 从 0/1 到「放东西」：一切皆编码

回访 1-03：计算机只认识 0 和 1，因为电路只有「通」和「断」两种状态。但你要存的明明是文字、照片、音乐、视频——这些东西怎么变成 0 和 1？

答案是**编码**：给每一种信息，约定一套「0/1 翻译规则」。

- **数字**：十进制转二进制（1-03.2），比如 5 → 101。
- **文字**：给每个字符一个编号，再存编号。字母 'A' 编号 65 → 存成 0/1；汉字也各有各的编号（这就是「字符集」干的事）。
- **图片**：把图切成密密麻麻的小格子（像素），每个格子存一个「颜色编号」。
- **声音**：把连续的声波切成无数个极短的时间片，每片存一个「音量数值」。

**所以「存东西」的本质，是往内存里的一排格子里放 0/1。** 内存就是一条长得望不到头的「格子带」，每个格子有一个地址（编号）。「存」= 往某个编号的格子里写，「取」= 从某个编号的格子里读。**记忆的物理基础，就是这排编了号的格子；而「数据结构」，就是「怎么分配和使用这些格子」的安排方式。**

（这里也顺带回收了原 5-04 的布尔逻辑：0 和 1 不只能「表示数」，还能「表示真假」——真=1、假=0。有了「真假」，就有了「与、或、非」的运算，而一切逻辑判断、一切条件分支，都从这三个字长出来。）

## 1.2 为什么需要「结构」：乱堆 vs 有货架

设想一个仓库：货物乱堆在地上，你要找一件东西，只能一件件翻；但如果有货架、有分区、有编号，你一步就能走到它面前。

数据也一样。**同样一堆数据，摆法不同，查找和修改的速度能差几千倍。** 「数据结构」就是给数据安排「货架」的方式——它决定了一件事：**当你想「找」「插」「删」某个数据时，要花多少步。**

这里藏着全书最该记住的一对矛盾：**时间（快） vs 空间（省）。** 有的结构查找快、但占地方大；有的结构省地方、但查找慢。**没有任何一种结构是「又快又省」的万能货架**——程序员做的，永远是在「时间」和「空间」之间做取舍。理解了这一点，你就理解了整个数据结构学科在忙什么：**它是在给不同的场景，定制不同的货架。**

## 1.3 数组（Array）：一排连续的格子

最简单的结构，是**数组**：把一堆数据，放进一排**紧紧挨着**的格子。

- 下标从 0 开始：第 0 个、第 1 个、第 2 个……
- **优点（查找快）**：因为格子连续，我知道第 0 个在哪，就能瞬间算出第 5 个在哪（地址 = 起点 + 5 × 每格大小）。这叫「随机访问」——**想找第几个，一步到位，O(1)**。

```
arr[0]  arr[1]  arr[2]  arr[3]
┌──────┬──────┬──────┬──────┐
│  猫  │  狗  │  鱼  │  鸟  │
└──────┴──────┴──────┴──────┘
取 arr[2]  →  "鱼"   （一步定位）
```

- **缺点（插删慢）**：如果我要在「猫」和「狗」之间插一个「蛇」，就得把「狗、鱼、鸟」整体往后挪一格——**中间插一个，后面全要动，O(n)**。

**类比**：电影院的一排座位。找「第 3 排第 5 座」很容易（按号数）；但要让一个人插到中间，后面整排人都得起身挪位。

## 1.4 链表（Linked List）：串起来的珠子

数组的毛病是「插删要挪一整段」。链表的解法是：**不让数据挨着，让每个数据「记住下一个在哪」。**

```
[猫]→[狗]→[鱼]→[鸟]→空
 每个珠子：存自己 + 存「下一个的地址」（指针）
```

- **优点（插删快）**：要在「狗」后面插「蛇」，只要让「狗」的指针指向「蛇」、「蛇」的指针指向「鱼」——**改两根链子，别的珠子都不用动，O(1)**。
- **缺点（查找慢）**：要找「第 3 个」，得从「猫」开始，沿着链子一个个数过去——**不能跳，只能走，O(n)**。

**类比**：一串珠子。你要加一颗、摘一颗，很容易；但你要数「第几颗」，只能一颗一颗顺着摸。

数组 vs 链表，是全章第一组对照，一句话记住：**数组「挨着放」，所以「找快、插慢」；链表「串着放」，所以「找慢、插快」。** 没有谁更好，只看你的场景是「查得多」还是「改得多」。

## 1.5 栈与队列（Stack & Queue）：两种排队方式

有些数据，我们只关心「先处理谁」，于是有了两种「只允许在特定位置操作」的结构：

- **栈（Stack）**：**后进先出（LIFO）**——后放进去的，先被拿走。像**一摞盘子**：你只能从顶上拿，最后放上去的盘子最先被拿走。
  - 操作：`push`（压入）、`pop`（弹出顶部）。
  - **现场**：浏览器的「后退」按钮（后看的页面先退回）、函数的层层调用（一个函数里调用另一个，返回时按相反顺序回）。

- **队列（Queue）**：**先进先出（FIFO）**——先到的先被服务。像**排队买票**：谁先排，谁先买。
  - 操作：`enqueue`（入队，从队尾进）、`dequeue`（出队，从队头出）。
  - **现场**：打印任务（先提交的先打印）、客服排队、消息队列。

一句话：**栈是「后进先出」的盘子堆，队列是「先进先出」的排队线。** 它们管的是「顺序」，不是「找得快」——很多「先处理谁」的问题，答案就是「用栈」或「用队列」。

## 1.6 哈希表（Hash Table）：直接"算"出位置

前面几个结构，查找都要「找」——要么按号（数组），要么顺链（链表）。哈希表想得更绝：**干脆不找了，直接「算」出它在哪。**

- 给每个数据一个「钥匙」key（比如姓名），用一个函数 `hash(key)` 把 key **换算成一个格子编号**，直接把数据放进那个格子。
- **查找**：再算一次 `hash(key)`，直接跳到那个格子取——**近 O(1)，几乎不看数据量大小**。

```
hash("张三") → 37  号格
hash("李四") → 05  号格
找 "张三"：算 hash("张三")=37 → 直接去 37 号格
```

**类比**：图书馆的检索号。你不需要在书架里一本本翻，只要「算」出这本书的检索号，直接走到对应书架。

它的代价是：两个不同的 key 可能「算」出同一个格子（这叫「冲突」），需要额外的办法处理。但核心思想极其值钱——**「查找」从「一个个试」变成了「直接算」**，这是它快到接近 O(1) 的秘密。

## 1.7 树与图（Tree & Graph）：层级与关系网

有些数据不是「排成一排」，而是「有层级」或「有千丝万缕的关系」，于是有了两个更自由的结构：

- **树（Tree）**：一个「根」，往下分叉，层层展开。像**文件夹**（一个文件夹里套多个文件夹）、**家谱**、**公司组织架构**。
  - 树天生适合「搜索」「分类」「排序」，很多高效的查找结构（如二叉搜索树）都是树的变种。

- **图（Graph）**：任意两个点之间，都可以连一条「边」，表达「谁和谁有关系」。像**社交网络**（人=点，好友关系=边）、**地图**（城市=点，道路=边）、**网页**（页面=点，链接=边）。
  - 图是「关系」的最通用表达：导航找最短路线、推荐「你可能认识的人」、网页排名，背后都是图。

**一句话**：树管「层级」，图管「关系」。它们比「排成一排」的数组链表更灵活，是搜索引擎、导航、社交 App 的地基。这一章先认识它们的长相，真正「怎么在树和图里搜」是下一章（算法）的事。

## 误区（本局小结）

1. **「数据结构有绝对的好坏」** —— 没有，只有「场景取舍」。数组找快插慢，链表插快找慢，哈希查快但占空间——选哪个，看你要「查得多」还是「改得多」。
2. **「存得快就一定取得快」** —— 常常相反：有的结构存进去很省事，取出来却很费劲（反之亦然）。「时间 vs 空间」是永恒的权衡。
3. **「数据结构是高级程序员才用的」** —— 每个 App 都在用：你的微信好友列表、购物车、浏览器历史，背后全是这些结构。它们不是「高深」，是「日用」。
4. **「栈和队列只是两种排队」** —— 它们决定了「先处理谁」的顺序：栈是后进先出（后退键），队列是先进先出（打印队）。顺序不同，行为天差地别。
5. **「哈希表是魔法」** —— 不是，是「把查找变成计算」：算一个编号，直接跳过去。核心是把「找」换成「算」。
6. **「树和图是两种完全不同的东西」** —— 树其实是「没有环的图」，是一种特殊的图。它们统一在「关系」这个更宽的概念下。
